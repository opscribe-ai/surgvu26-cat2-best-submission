SurgVU 2026 · Category 2 · Data plan

What we need to collect, and how

Four trainable components — and almost all the labels already exist inside the two CSV files we've had since day one. The work is not annotation. It's deriving labels from intervals, extracting frames at scale, and avoiding three traps that would quietly poison the training set.

First: a measurement that changes the design

The tool recogniser was specified as a constrained top-3 selection — always exactly three instruments, because the da Vinci has four arms and one holds the camera. I checked that against the actual label tables rather than trusting the challenge's prose.

Sampling ~10,800 timestamps inside task segments (which is where test clips come from), after removing duplicate rows and part-spanning intervals:

"Exactly three" is a strong prior, not a hard constraint. It holds for 78% of sampled timestamps overall, and 82% of those with at least one instrument installed.

So hard-constraining the output to exactly three would force a wrong answer roughly one time in five. Revised: 12 independent sigmoid outputs, threshold tuned on validation, with the observed cardinality distribution used as a soft prior rather than a constraint. Top-3 remains the tie-break when the thresholded set is ambiguous.

The 4-and-above cases are almost certainly genuine tool exchanges, where a replacement is installed before the outgoing instrument is recorded as removed. The 0-tool cases are real gaps. Neither is a data error; both are reasons the constraint has to be soft.

On the detector — my recommendation changed

I had assumed there were no bounding boxes available and that training a detector meant solving Category 1's weak-supervision problem from scratch. The download page labels cat1_test_set_public.zip as a validation set, and it carries clevis bounding boxes — so real boxes do exist, in-domain.

Even so, I'd still start with an off-the-shelf open-vocabulary detector (GroundingDINO or OWLv2) and train nothing. The detector is only an arbiter: it needs to beat a whole-frame classifier on occluded instruments, not to be state of the art. If measurement shows it's the weak link, fine-tune on the Cat 1 validation boxes then. Training it first would be the single largest time sink in the project, spent on the least certain component.

There is also a fifth trainable thing that needs no video at all: the learned router gate. It trains on the synthetic Q&A validation set, mapping (question type, perception outputs, confidence) to a branch. Cheap, and it comes last.

The unit of training data

Test clips are 30 seconds, sampled at 1 fps. So that is the unit we train on — a 30-second window, 30 frames, labelled with the instruments installed, the task, and its description. Matching test conditions exactly removes a whole class of distribution mismatch, and it is also what the 2025 winner did.

840 hours yields roughly 100,000 non-overlapping windows. We do not need all of them. Target ~25,000 windows, stratified by tool class and task so the rare instruments are not drowned out.

The efficiency that matters

Extract the frame pool once; derive three training sets from it. The tool recogniser, task classifier, and action model all want frames from the same windows — they differ only in labels and in how many consecutive frames they consume. Decoding 344 GB of 60 fps video is the expensive step, and it should happen exactly once.

Storage: 25,000 windows × 30 frames ≈ 750,000 JPEGs. Cropped to roughly 896×675 and saved at quality 85, that lands around 40–50 GB — comfortable inside the 2,000 GB staging allocation, alongside the 344 GB archive.

Three traps that would poison the training set

Trap 1 — the answer is printed on every training frame, and using it is banned

Every training video carries a UI bar burned into the bottom listing the instrument on each arm by commercial name, plus the endoscope angle: 

1  MEGA NEEDLE DRIVER   2  [scope] 1x 30°   3  MEGA SUTURECUT NEEDLE DRIVER   4  SMALL GRASPING RETRACTOR

It is legible in all 11 Cat 2 sample clips and matches ground truth exactly. It is also explicitly out of bounds: "using the information available in the UI to make predictions is not allowed. To enforce this, the UI will be blurred from the test set eliminating this information."

So blurring is compliance, not tuning. A model trained on unblurred frames uses UI information to make predictions whether we intended it or not — and would then collapse at test, where the bar is gone. Crop 192 px from each side and Gaussian-blur the bottom 45 px with a 51-pixel kernel, identically at training and inference. Match the organizers' published example blurred frame rather than approximating it, so the CNN sees the same distribution in both places.

This is also why the 2025 winner blurred the bar before inference, and it closes the commercial-name question in the negative: the one place that information appeared is removed by construction, so Large versus Mega is genuinely unrecoverable from pixels.

Trap 2 — splitting by frame instead of by case

Frames from the same session are near-duplicates. A random frame-level split puts near-identical images in train and validation, and every number you measure becomes fiction. Split by case — one canonical split file, ~124 train / 31 validation, used by every model so results stay comparable.

Trap 3 — the part boundary

Cases are split into up to two video parts and timestamps reset at the boundary (mean 1.77 parts per case). Both CSVs carry *_part columns for exactly this reason. Ignore them and you will label frames from part 2 with part 1's tools. The tell that this is already biting: naively summing task durations gives negative hours for rectal artery/vein, because segments spanning the boundary have stop_time < start_time.

A fourth, smaller one: tasks.csv in the Cat 2 label set has 50% duplicate rows (3,673 rows → 1,850 unique). tools.csv is clean by comparison (7 duplicates in 8,885). Dedupe tasks before computing anything.

How we build it, on CHTC

1Label engine — pure Python, no video, build first

One function, shared by everything downstream: labels_at(case, part, seconds) → {installed_tools, task, description}. It parses both CSVs into interval trees, dedupes, respects part boundaries, and maps the 20 raw classes down to the 12 that matter. Testable in isolation against the 557 KB label file we already have — no video required, so it can be written and unit-tested today.

2Frame extraction — 280 embarrassingly parallel Condor jobs

One job per video file. Each pulls its video from staging, decodes once, emits the sampled windows as a tar shard, writes the shard back, exits. This is the shape HTCondor is best at, and it turns a multi-day serial decode into a few hours of wall clock. 

for each video:
    windows = stratified_sample(labels, n≈90 per video)
    for w in windows:
        frames = decode(w.start, w.start+30s, fps=1)   # 30 frames
        frames = crop_sides(frames, 192)               # black margins
        frames = blur_bottom(frames, 45, kernel=51)    # the overlay — never skip
        write_shard(frames, labels_at(w))

3Canonical split — one file, every model

splits.json: ~124 training cases, ~31 validation cases, chosen once and stratified so rare instruments appear on both sides. Every model reads it. Never regenerate it.

4Train, in dependency order

  1. Tool recogniser — optionally SurgToolLoc-pretrained, then fine-tuned. Needed by everything else.
  2. Task classifier — same frame pool, different labels. Unlocks description retrieval, which is the single biggest scoring advantage.
  3. Action recogniser — weakest supervision, so it is gated: if it does not beat the VLM on action questions in validation, drop it and route those questions back through dense re-sampling.
  4. Detector — off the shelf, zero training, unless measurement says otherwise.

Before training anything — four checks

These are cheap, and each one can invalidate a component. Run them the moment the first shard lands.

  1. Eyeball 50 frames against their derived labels. Does a frame labelled "monopolar curved scissors" actually show scissors? This single check validates the entire time-base alignment — part handling, timestamp parsing, interval logic — and nothing downstream is trustworthy until it passes.
  2. Confirm the blur mask covers the overlay in every case. The 45 px figure comes from the 2025 winner's code and assumes a consistent layout. Verify on a sample spanning many sessions before committing 25,000 windows to it.
  3. Check the cardinality distribution on extracted windows matches the 78/82% figures measured above. A large deviation means the extraction is sampling somewhere the label engine and I disagree about.
  4. Train a deliberately tiny tool classifier on 2,000 windows. If it cannot beat chance, something is wrong with the labels, not the model — and finding that out costs an hour rather than a week.
The check I would not skip

Number 1. Every label we use is derived from timestamps rather than read off a frame, so a single off-by-one in part handling or timestamp parsing would silently mislabel the entire corpus in a way that no loss curve would reveal — the model would simply learn the wrong thing confidently.
