## What Failed and Why

### Attempt 1: The 16-burst pool would fix the temporal deficit
**What:** Extracted `shards_multi16` (16 bursts x 3 frames = 48 frames/window)
to remove the coverage handicap that made every earlier 3D arm see 4 moments
against the 2D model's 16.
**Result:** The pool is correct and verified, and the arms trained on it still
found nothing.
**Root cause:** Coverage was never the binding constraint. See Attempt 6.

### Attempt 2: The memory rescue was a livelock, and running it on a timer fed it
**What:** `release_held.sh` released every held extraction job at a flat 8192 MB.
**Result:** Five 160-window cases measured 9,766 MB, so each was held for
JobOutOfResources, released at 8192, killed, held again. proc 6 went round SIX
times over 74 minutes while the shard count sat still.
**Root cause:** A rescue that always offers the same amount cannot rescue a job
needing more, and I was calling it from wait loops, sustaining the cycle. It
now escalates from the MEASURED peak (1.5x) and can never hand a job less than
it just died at. A 160-window case at 48 frames holds 6.04 GB of raw frames.

### Attempt 3: A segfault reported as a clean test pass
**What:** Routine test run, cluster 9660217.
**Result:** SIGSEGV at 69% of the suite. `run_tests.py` reported "0 total, 0
environmental, 0 real" and exited 0. HTCondor recorded success. I had been
reading those results all morning.
**Root cause:** Every number the harness produced was parsed from lines pytest
PRINTS. A run that dies before printing them counts zero failures, and zero
failures is indistinguishable from clean. Fixed: the harness now asks whether
pytest FINISHED (negative rc = signal; rc outside {0,1}; no summary line) and
records `completed`. The crash itself was my own test subclassing
`cv2.VideoCapture` -- a C-extension type not built for it. Rewritten to delegate.

### Attempt 4: The cutting rule, gated on motion
**What:** `_answer_cutting` answers "is tissue being cut?" with "are scissors
visible?". The plan was to gate it on measured motion.
**Result:** REJECTED after calibration. 471 windows hold a credible cutting
tool; 46 (9.8%) fall in the bottom activity decile, so the rule would flip about
one cutting answer in ten from Yes to No.
**Root cause:** The router already documents, from measurement, that gold polar
answers in this corpus skew Yes and that `credible_tools` is deliberately
PERMISSIVE because a wrong Yes is cheap. There is **no cutting label in this
corpus** to establish that any of those 46 flips is right. Shipping it would bet
against a measured prior on unvalidated evidence. `STATIC_ACTIVITY_THRESHOLD`
stays None.

### Attempt 5: I reintroduced the v4 aggregation bug
**What:** `train_sequence_cached.py` evaluated by squashing the MEAN LOGITS.
**Result:** Reported the alpha=0 base as 0.9415 / 0.9538 while the dump of the
same checkpoint on the same windows said 0.9454 / 0.9577.
**Root cause:** `softmax(mean(logits))` is not `mean(softmax(logits))` -- the
bug that cost 0.0145 and most of a night in v4, written again in a new file
three weeks later. Both forms are one line and both produce plausible
probabilities. Caught only because the trainer prints its base next to a number
established independently. Evaluation now averages probabilities; the LOSS still
averages logits, matching `train_temporal.py`.

### Attempt 6: THE EXPERIMENT -- the 30 s sequence branch on the task head
**What:** Six configurations trained on cached features against an alpha=0 base
of **0.9577** established through the same pipeline.

    config                    params    honest   h.gain   naive gain    bias

**Result:** Best honest gain **+0.0002** -- one window in 4,635. No configuration

**Root cause (why this is a real null, not a tuning failure):** the trend is

ordinary way -- best epoch on val -- this sweep is six consecutive "wins" of
exactly the size this project treats as a result, all artefacts. **Without the
fold protocol added at 14:04, today would have shipped "+0.0024, the 30 s branch
helps".** The bias scales with capacity (0.0060 at 1.1M params, 0.0015 at 75k),
which is what theory predicts.

## Key Decisions Made

- **THE BASE-NUMBER TRAP. The tools base on `shards_multi16` is 0.7673, not
  0.7802.** 0.7802 is the 2D head on the SPARSE pool; the burst centres sit up
  to 0.438 s from the sparse pool's 1 fps grid. An arm at 0.7750 has beaten its
  base by +0.0077 and will read as a 0.0052 regression against the remembered
  number. Diagnosed, not assumed: macro-F1 averages 12 classes with support from
  29 (stapler) to 2308, so 4-5 flipped windows IS the 0.0129; threshold and
  probability perturbation were both measured and ruled out; the TASK head
  reproduces to -0.0004 through the identical code path.
- **The motion gate stays CLOSED** (Attempt 4). A 24-case test asserts adding a
  motion block changes no answer, and it asserts the gate is closed, so it starts
  failing the moment someone calibrates a threshold without revisiting the rules.
- **`--motion` is OFF by default in serving.** Measured cost is only +6%
  (6.6 s -> 7.0 s per case), so cost is NOT the argument -- it buys nothing today
  and an unused feature in a shipped path rots.
- **No confirmation dump of the trained arm.** It does not clear its base, so
  nothing depends on the number, and trainer-vs-dump agreement was already
  established at beta=0 to four decimals. Had a config cleared its base, the dump
  would have been mandatory.
- **The local 0.2 s branch is deprioritised**, on three independent grounds: the
  calibration pointed at the task head; its per-burst corrections are
  order-invariant after the mean (a window and its reverse score identically);
  and it cannot use the cache (~696 GB of spatial maps) so each arm is ~1.6 h per
  epoch against two minutes.
